# Prompt Engineering — Создание надежных промптов

Этот навык используется для проектирования, доработки и тестирования промптов, где надежность и точность важнее «креативности». Основан на производственных паттернах анализа документов и агентных рабочих процессов.

## 🎯 Цель
Создать промпт, который минимизирует галлюцинации, строго соблюдает формат вывода и стабильно выполняет сложные инструкции.

## 🛠️ Пять базовых правил (Load-bearing rules)

1. **Сразу обозначь задачу, роль и цель.** Первый абзац должен быть максимально конкретным. Без «разогрева» и лишних вступлений.
2. **Разделяй инструкции и динамические данные.** Используй XML-подобные теги для изоляции данных пользователя (например, `<data>`, `<sketch>`, `<context>`). Это предотвращает «утечку» инструкций.
3. **Давай пошаговые инструкции.** Нумерованный список. Одно действие — один шаг.
4. **Few-shot для сложных случаев, а не для простых.** Приводи примеры именно для тех краевых случаев (edge cases), на которых модель обычно ошибается. Включай в примеры цепочку рассуждений (reasoning trace).
5. **Повторяй критические ограничения в конце.** Эффект «свежести» (recency bias) заставляет модель лучше соблюдать правила, если они продублированы перед самым ответом.

## 🏗️ Структура продакшн-промпта (Порядок блоков)

1. **System Prompt (Стабильный):** Роль, цель, статические знания о домене (схемы данных, значения строк), спецификация формата вывода.
2. **Few-shot примеры:** 2–4 случая. Приоритет — сложные примеры с идеальным путем рассуждения.
3. **User Turn (Динамический):** Сами данные для анализа, обернутые в именованные XML-теги.
4. **Финальное напоминание:** 3–5 буллитов с «незыблемыми» правилами (не выдумывать, цитировать источник, обрабатывать неуверенность).
5. **Pre-filled Assistant Turn:** Начало ответа модели (например, `{` для JSON или `<final_verdict>`), чтобы жестко зафиксировать структуру.

## 🛡️ Чек-лист по борьбе с галлюцинациями

- [ ] Промпт велит модели утверждать только то, в чем она уверена.
- [ ] Четко определено действие при неуверенности (вернуть `null`, `uncertain` или воздержаться).
- [ ] Порядок рассуждений: сначала структурированные/фактические данные $\rightarrow$ затем неоднозначные.
- [ ] Каждое фактическое утверждение в ответе должно содержать цитату или ссылку на фрагмент источника.
- [ ] В финальном напоминании есть фраза «не выдумывай детали».

## 📦 Форматирование вывода

- **Для программной обработки:** Запрашивай JSON со строгой схемой.
- **Для извлечения человеком:** Оборачивай ключевое поле в уникальный тег (например, `<final_verdict>...</final_verdict>`).
- **Главный лайфхак:** Используй pre-filling (предустановку первого токена) для гарантии соблюдения формата.

## 🔄 Интеграция с Hermes

При создании промптов через этот навык:
- Используй `memory` для сохранения итераций промпта.
- Сохраняй финальные шаблоны через `skill_manage` в соответствующие навыки.
- Тестируй промпт по циклу **Concept $\rightarrow$ Action $\rightarrow$ Verify**.

## 🏁 Верификация
- [ ] Промпт содержит роль и цель в начале.
- [ ] Данные отделены тегами.
- [ ] Есть хотя бы один сложный few-shot пример.
- [ ] Критические ограничения повторены в конце.
- [ ] Определен формат вывода и способ обработки ошибок.
